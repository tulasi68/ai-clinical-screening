# Compliance hardening status

Branch: `main`

This is an engineering status record, not a legal compliance certificate. MediLoop and this service remain separately deployed; MediLoop calls this service through its server-side API credential.

## Implemented in this branch
- Patient `/start` requires a ledger-backed active consent or an affirmative consent flag with the exact notice version. New grants are written as separate server-generated consent events before screening continues.
- Consent timestamp is generated by the server, not accepted from the browser. The append-only event ledger stores version, language, method, channel, purpose and actor type separately from the mutable screening session.
- Patient `/message`, summary edits and `/submit` check the latest active ledger event. A patient-facing withdrawal control is available during questions, review and after submission; withdrawal is recorded as a separate event and stops further screening.
- All `/api/*` responses, including service-to-service screening reads, receive `Cache-Control: no-store` and related anti-cache headers.
- Service-side screening creation requires an authenticated `x-clinic-id` header matching the clinic ID in the request body. Service-side screening detail and output reads require the same header to match the clinic stored on the screening session; cross-clinic IDs return not-found.
- This scope is enforced in addition to the shared service API key. The API key remains a high-value shared credential and still needs rotation, least-privilege and operational controls. Global headers include `Referrer-Policy: no-referrer`, anti-framing, MIME-sniffing protection, same-origin resource policy and a restrictive content-security policy.
- The browser sends the notice version; its client-supplied consent timestamp has been removed.

## P0 hardening update (2026-11-01)

- Added clinic-key-map authentication in `src/security.js`. On managed runtimes, a shared key is rejected unless an explicit migration flag is enabled; malformed tenant-key JSON fails closed. **Rollout blocker:** `SCREENING_CLINIC_API_KEYS_JSON` must be provisioned with one independently generated credential per clinic in both deployments, and the legacy shared-key migration window must be deliberately decided. No production secrets were changed here.
- Added one-time link redemption using a conditional D1 `UPDATE ... RETURNING`, exchanging the URL bearer token for a short-lived HttpOnly, SameSite=Lax cookie. The URL token is consumed atomically and expires/replay-denies. Session state is preserved during exchange; the UI removes the token from the address bar. Cookie security depends on HTTPS/managed-runtime configuration.
- Revocation now updates only token credential columns instead of rewriting the session document, reducing the risk of overwriting concurrent patient answers.
- Consent-event timestamps are generated by the store, ignoring caller-supplied time. The server uses the returned ledger timestamp when reflecting the event in session metadata.
- Patient summary reads are gated by active consent; service reads of session/output are also gated by active consent.
- Added tenant credential helper tests and patient token/consent tests. The tests currently exercise helper/store behavior with a fake D1 adapter; they are not a substitute for live D1 concurrency and HTTP integration tests.

- Invalid, expired, revoked or replayed URL tokens now fail closed instead of falling back to whichever patient session cookie is present in the browser. This prevents a stale link from accidentally selecting a different patient's active session. The same rule applies to the redemption endpoint; successful redemption is followed by URL cleanup in the client.

## P0 hardening update — 2026-11-01

### Implemented in source on `main`
- Consent event timestamps are generated inside the storage layer; caller-supplied timestamps are ignored. The D1 schema already has triggers rejecting consent-event UPDATE and DELETE operations.
- Patient URL tokens are atomically exchanged using a conditional D1 UPDATE for a short-lived session credential. The credential is delivered only as an HttpOnly, SameSite=Lax cookie (Secure on managed/HTTPS runtimes); the browser removes the URL token from the address bar after successful exchange. The original URL token digest is replaced, so replay from a browser without the session cookie fails. Session content, status, conversation and existing consent history are preserved during exchange.
- Patient session reads return only minimum welcome/status data before active consent; conversation and output reads require the current purpose and notice version. Service-to-service detail/output endpoints also require active consent and clinic scope.
- Consent withdrawal appends a server-timestamped event, stops further processing and revokes the active patient session credential. Token revocation updates only credential columns, avoiding a read/overwrite race with the full session document.
- Service authentication supports unique per-clinic keys through `SCREENING_CLINIC_API_KEYS_JSON`. Managed runtimes reject shared-key-only authentication unless the temporary compatibility flag `SCREENING_ALLOW_SHARED_API_KEY=true` is explicitly set. Prefer unique keys per clinic; the shared flag is not tenant isolation.
- Added store tests for one-time redemption/replay, expired/revoked links, server-generated consent timestamps and consent state transitions; added pure tests for cross-clinic service credential denial.

### Verification evidence
- `npm run test:security` now includes both store and tenant-auth tests; `npm run check` syntax-checks the server, store, security helper and browser app. These scripts have not been executed locally in this connector session; GitHub Actions results must be checked after commit.
- The implementation has not been deployed. The D1 migration/binding, current live Worker version, cookie behavior and MediLoop end-to-end integration have not been production-verified.

### P0 rollout blockers and risks
- **Do not deploy until matching per-clinic keys are configured on both independent deployments.** Configure the same unique key for each clinic in `SCREENING_CLINIC_API_KEYS_JSON` and `CLINICAL_SCREENING_API_KEYS_JSON`. No secrets were changed. If only the old shared key is configured, the new managed-runtime Screening code fails closed unless the temporary compatibility flag is explicitly enabled.
- The one-time exchange reuses existing credential columns, so it introduces no schema migration. An in-progress patient can resume only in a browser holding the session cookie after first redemption; opening the consumed URL in another browser fails. A future separately stored resumable-link credential is needed before re-issuing links after submission; the consumed URL is no longer sent again through the post-submit WhatsApp path.
- Existing sessions without an active versioned consent event are not allowed to expose previous answers/output. They must re-affirm consent before the UI returns to the review flow; test this against real legacy records before rollout.
- The D1 fake verifies conditional update behavior but is not a concurrency test against real D1. Verify atomic replay denial, D1 schema, expiry, cookie attributes, withdrawal and all patient/service routes in a staging Worker before production.
- Distributed rate limiting, platform/log redaction, retention/deletion propagation, backup expiry and legal-hold workflows remain open. The prior Supabase project and data have not been modified or deleted; D1 deployment and any required export/reconciliation remain pending.

## Follow-up source audit (2026-11-01)

Two additional release blockers were identified during review and are intentionally not represented as fixed:

- **Patient-link host trust:** `patientUrl()` falls back to the request `Host` header when `PATIENT_APP_URL` is unset. Before sending patient links, configure a canonical HTTPS patient-app origin and reject untrusted/missing origins in managed deployments. Verify proxy host validation and add tests for hostile Host / forwarded-host values. Do not rely on request-derived host values for bearer-link destinations.
- **Deletion vs append-only consent conflict:** `screening_consent_events.screening_id` references sessions with `ON DELETE CASCADE`, while a trigger rejects every consent-event DELETE. A session deletion that cascades to consent rows will therefore be blocked. Define a legally reviewed retention/deletion design (for example, separately retained minimal audit evidence with a documented lawful basis and expiry, plus deletion of clinical payloads) and implement a migration + tests before enabling deletion workflows. Do not remove the append-only triggers or alter retention policy without that decision.
- **Normalization regression candidate:** source inspection found the store's phone/specialty normalization regexes appear double-escaped (`/\\\\D/` and `/\\\\s+/` in source text). Confirm in a local Node test and correct alongside tests for punctuation in phone numbers and whitespace in specialty names before release.

These findings were source-reviewed only; no runtime tests, D1 migration, deployment, or production configuration change was performed in this follow-up.
