# Compliance hardening status

Branch: `main`

This is an engineering status record, not a legal compliance certificate. MediLoop and this service remain separately deployed; MediLoop calls this service through its server-side API credential.

## Implemented in this branch
- Patient `/start` requires a ledger-backed active consent or an affirmative consent flag with the exact notice version. New grants are written as separate server-generated consent events before screening continues.
- Consent timestamp is generated by the server, not accepted from the browser. The append-only event ledger stores version, language, method, channel, purpose and actor type separately from the mutable screening session.
- Patient `/message`, summary edits and `/submit` check the latest active ledger event. A patient-facing withdrawal control is available during questions, review and after submission; withdrawal is recorded as a separate event and stops further screening.
- All `/api/*` responses, including service-to-service screening reads, receive `Cache-Control: no-store` and related anti-cache headers.
- Service-side screening creation requires an authenticated `x-clinic-id` header matching the clinic ID in the request body. Service-side screening detail and output reads require the same header to match the clinic stored on the screening session; cross-clinic IDs return not-found.
- This scope is enforced in addition to the shared service API key. The API key remains a high-value shared credential and still needs rotation, least-privilege and operational controls. Global headers include `Referrer-Policy: no-referrer`, anti-framing, MIME-sniffing protection, same-origin resource policy and a restrictive content-security policy.
- The browser sends the notice version; its client-supplied consent timestamp has been removed.

## P0/P1 items still open
- The patient URL remains a bearer credential until revoked. Immediate revocation is now implemented; one-time URL redemption into a secure HttpOnly session, distributed rate limiting and token redaction from logs/analytics remain open.
- Verify tenant and doctor authorization on every service API and every database operation.
- Review Supabase service-role access. It bypasses RLS; server-side tenant checks must be enforced and tested.
- **Migration required before deployment:** `supabase/migrations/20261031_screening_consent_event_ledger.sql` creates the append-only table, denies UPDATE/DELETE via trigger, restricts access to service role and backfills existing affirmative consent snapshots. It has been committed but not applied to the live Supabase project. Until applied, consent ledger reads/writes fail closed and patient screening cannot proceed.
- Add retention, deletion propagation, backup expiry and legal-hold workflows across sessions, outputs, logs and processors.
- Inventory all processors, outbound data transfers, telemetry and error logging; prove clinical data is not sent to unapproved services.
- Existing in-progress sessions without the new versioned consent record will be blocked until the patient re-affirms consent. Test this behavior before rollout.

## P2 governance and evidence
Maintain a processing inventory, data-flow diagram, processor register, retention schedule, incident/breach response procedure, grievance and rights-request workflow, test evidence, release approvals, dependency/SBOM scans and vulnerability remediation records.

## Acceptance tests required
1. Missing, false, stale-version and withdrawn consent cannot start, answer or submit.
2. Expired, revoked, replayed and cross-session patient tokens fail safely.
3. Cross-clinic and cross-doctor access is denied regardless of client-supplied identifiers.
4. Deletion covers sessions, outputs, backups, logs and downstream processors.
5. Automated negative tests and production configuration evidence support each control.

## Regulatory scope to validate
Assess DPDP Act 2023 and DPDP Rules 2025 according to the Gazette commencement schedule provision-by-provision; IT Act 2000, applicable SPDI Rules 2011 during transition and CERT-In directions; ABDM Health Data Management Policy, HIE/Consent Manager specifications and ABHA onboarding requirements; and clinical establishment, record-retention and medical-device/software obligations as applicable. Obtain legal review. Code changes or an ABDM label do not establish compliance.
